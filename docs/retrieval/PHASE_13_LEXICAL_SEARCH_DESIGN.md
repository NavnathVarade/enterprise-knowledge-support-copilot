# Lexical Search — Phase 13

## Scope delivered
- A second real migration (`migrations/versions/0002_chunk_fulltext_search.py`): a `STORED`
  generated `tsvector` column on `document_chunks` plus a GIN index, hand-written rather than
  autogenerated for reviewability
- `packages/database/repositories/lexical_search.py` — tenant-scoped full-text search over
  chunks, ranked by `ts_rank_cd`

## Honest naming: this is not BM25
The brief asks for "BM25 or equivalent". Postgres full-text search plays the same *role*
(a lexical, term-matching retriever that complements dense vectors) but `ts_rank_cd` is not
BM25 — it scores by term frequency and cover density within a single document, with no
corpus-wide inverse-document-frequency term. A rare, highly discriminating word is not
automatically weighted above a common one the way real BM25 would weight it. Accepted here
because it's index-backed, tenant-filterable in the same SQL statement as a future vector
join, and needs no extra service — but recorded as a real limitation for Phase 28's retrieval
evaluation to weigh in on, not asserted as equivalent quality.

## A real design bug, caught by its own test before this was ever "done"
The first implementation used `websearch_to_tsquery`, which **ANDs** terms together. That
failed `test_matching_chunk_is_returned_and_unrelated_is_not` outright: a chunk containing
"refund" but not "policy" was correctly indexed but never returned for the query "refund
policy," because AND semantics require every term to match. For a RAG system this is a real
recall bug, not a theoretical one — a natural-language question routinely contains words the
answering chunk doesn't. Rewritten to OR semantics (`plainto_tsquery`'s normalized output,
rewritten from `&` to `|` and re-parsed), with `ts_rank_cd` still ordering fuller matches
above partial ones — proven by `test_chunk_matching_more_query_terms_outranks_one_matching_
fewer`, which checks both that a partial match is still admitted (recall) and that the fuller
match ranks first (precision).

## Proof, not assertion
Thirteen tests against a real Postgres: relevance ordering, English stemming ("entitle" ↔
"entitled"), a dedicated stop-words-only query, tenant isolation (including a query for
identical text seeded under two different tenants), five parametrized hostile-input cases
(SQL-injection-shaped strings, unbalanced quotes, `tsquery` operator characters, a 2000-char
string, a bare backslash) proving the query function never raises and never damages the
table, and — critically — `test_gin_index_is_used_by_the_planner`, which sets
`enable_seqscan=off` and inspects a real `EXPLAIN` plan to confirm the GIN index is actually a
valid, chosen access path for the exact predicate this code emits, not just present in the
schema.

## Not yet implemented (explicitly, not silently)
- **No hybrid fusion yet** — this phase only proves the lexical leg works correctly in
  isolation. Combining it with vector search (Reciprocal Rank Fusion, per ADR-006) is
  Phase 14.
- **English-only.** `to_tsvector('english', ...)` is hardcoded; multi-language support would
  need a per-document or per-tenant language configuration.
- **Users cannot use quoted-phrase or exclusion syntax** (`"exact phrase"`, `-term`) — the
  OR-rewrite trade-off means `plainto_tsquery`'s phrase/negation handling is not preserved.
  Acceptable for the recall-first role this leg plays ahead of reranking, flagged here for
  whoever builds a query-syntax-sensitive UI later.
