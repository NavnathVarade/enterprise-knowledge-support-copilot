# Phase 29 — Observability, Tracing and Audit (Spec §59–65)

## What exists
| Area | Implementation |
|---|---|
| Metrics | `packages/observability/metrics.py` — one dedicated registry, `ekc_` namespace, bounded labels only |
| Exposure | API `GET /metrics` and worker port `OTEL_METRICS_PORT` (default 9102). **Fail-closed:** no `OTEL_METRICS_BEARER_TOKEN` ⇒ endpoint returns 404 / port is not opened; token compared in constant time |
| Tracing | `packages/observability/tracing.py` — OpenTelemetry, ParentBased ratio sampling, OTLP export when `OTEL_EXPORTER_OTLP_ENDPOINT` is set; W3C `traceparent` carried in `EventEnvelope`, so upload → relay → worker is one trace |
| Log correlation | every log line gains `otel_trace_id` / `otel_span_id` when a span is active |
| Audit | `audit_events`: append-only (DB triggers), per-tenant gapless sequence, SHA-256 hash chain, allow-listed details; `GET /api/v1/audit` and `/audit/verify` for `admin` / `security_auditor` |
| Alerts / dashboard | `monitoring/prometheus/alerts.yaml` (13 rules), `monitoring/grafana/ekc-overview.json` (12 panels) |

## Privacy and cardinality rules (tested)
- No metric label carries tenant, user, document, query, filename or error text. Per-tenant
  detail lives in logs, traces and the audit trail.
- Span attributes are limited to counts, ids, hashes, enums; keys like `query`, `prompt`,
  `text`, `email` are dropped and long strings are replaced. A test sends a query containing a
  distinctive phrase and asserts it appears in no span and no metric.
- Audit `details` use an allow-list (`route`, `status`, `query_hash`, `mime_type`,
  `size_bytes`, `reason`, `error_code`, …). Anything else raises at write time. Login records
  never contain the email or password; queries are stored only as a 12-hex hash.
- Alert and dashboard queries are checked against the registry: every metric and label they
  mention must exist (`tests/unit/test_metrics_and_tracing.py`).

## Audited actions
`auth.login` (success/denied, for known tenants), `document.upload` (written in the SAME
transaction as the upload), `query.executed`, `query.denied` (permission/authorization/rate
limit). Login and query auditing are **best effort**: a failed audit write is counted in
`ekc_audit_write_failures_total` (page-level alert) and does not fail the user's request.
Uploads are strict: no audit row, no upload.

## Verified vs not verified
Verified against real Postgres/Redis and in-process OTel exporters: metric movement on real
requests, route-template labelling, 404/401/200 behaviour of `/metrics`, span nesting and
error status, trace continuity across the event envelope, privacy assertions, append-only
triggers, hash-chain tamper and gap detection, gapless sequence under 12 concurrent writers,
role gating and tenant scoping of the audit API.

**NOT verified:** OTLP export to a real collector; a real Prometheus scrape, `promtool check
rules`, or Grafana import; consumer-lag reporting against a real broker (the reporter is
reviewed against confluent-kafka's API and tested with a fake). Alert thresholds are
**untuned placeholders** — there is no production traffic to calibrate them.

## Known limits
- Audit tamper evidence stops at a database superuser who can drop the triggers *and* rewrite
  every later row. Anchoring chain heads in external WORM storage is not built.
- Failed-login audit rows can still be generated by anyone who knows a tenant slug; since Phase 32
  logins are throttled per IP and account (`ekc_login_throttled_total`), which bounds but does not
  prevent inflating the table. Unknown-tenant attempts are not audited.
- Audit retention/archival (Spec: 7 years) is not implemented; the table only grows.
- Not yet audited: document reads, comparison, ACL changes (no ACL-change API exists yet),
  admin actions, and every worker-side state change.
- Lag is exported only when a process calls `report_consumer_lag` periodically; the worker
  entrypoint does not schedule it yet.
- No SLOs/burn-rate alerts, no exemplars, no log shipping config, no business metrics.

## Runbook

### EkcApiHighErrorRate
**Fires when:** 5xx share above 5% for 10m.

**First checks:** Check `ekc_http_requests_total` by route to find the failing endpoint; check /api/v1/health/ready (database/redis); look for `unhandled_exception` log lines by request_id; check a recent deploy.

### EkcApiLatencyP95High
**Fires when:** Non-query p95 above 2s.

**First checks:** Per-route latency panel; database connection saturation and slow queries (statement_timeout is applied); Redis latency.

### EkcQueryLatencyP95High
**Fires when:** Query p95 above 20s.

**First checks:** LLM latency panel and `ekc_llm_requests_total` outcomes; retry rate (`ekc_llm_retries_total`); reranker/embedding provider latency in traces (`query.run` children).

### EkcAbstentionRateHigh
**Fires when:** Over 50% abstentions for 1h.

**First checks:** Break down `ekc_answer_abstentions_total` by reason. NO_CONTEXT => retrieval/ingestion problem (check ingestion failures, consumer lag, ACL changes); LOW_EVIDENCE => reranker/embedding quality; MODEL_ABSTAINED => prompt or provider change.

### EkcLlmFailureRatioHigh
**Fires when:** Over 10% of LLM calls failing.

**First checks:** Outcome label tells the cause (timeout, unavailable, rate_limited, invalid_response). Check provider status page and API key validity; confirm the fallback provider is configured.

### EkcOutputPolicyViolation
**Fires when:** A model output was blocked (prompt-leak shingle, markdown image, unlisted URL, canary).

**First checks:** Treat as a possible attack or prompt regression. Find the request via logs (`output_policy_violation`), review the audit trail for the actor, check the document set for injected content.

### EkcInjectionQuarantineSpike
**Fires when:** More than 20 chunks quarantined in 1h.

**First checks:** A newly ingested document may contain injection text. Query logs for `chunk_quarantined` to get document ids, review and remove or re-classify the source.

### EkcAuditWriteFailures
**Fires when:** Audit events not written.

**First checks:** Page-level: compliance gap. Check database health and the append-only triggers; failed events are only in application logs until fixed.

### EkcKafkaConsumerLagHigh
**Fires when:** Lag above 1000 for 10m.

**First checks:** Consumer replicas running? Look at handler duration and DLQ rate; scale ingestion workers; check embedding provider latency.

### EkcDeadLetteredMessages
**Fires when:** Messages dead-lettered.

**First checks:** Inspect the `.dlq` topic: DLQ envelopes show error_type; poison records carry raw base64 payloads. Fix cause, then replay (replay tooling is NOT built yet).

### EkcOutboxBacklogAging
**Fires when:** Oldest outbox row older than 5m.

**First checks:** Is the relay running? Kafka reachable? `ekc_outbox_relay_events_total{result="failed"}` and `last_error` on the rows say why. Rows are safe: they publish once the relay recovers.

### EkcOutboxPublishFailures
**Fires when:** Relay publish failures for 10m.

**First checks:** Broker auth/connectivity; message size; look at `outbox_events.last_error`.

### EkcIngestionPermanentFailures
**Fires when:** More than 5 permanent ingestion failures in 1h.

**First checks:** Query `document.processing.failed` events / documents in `processing_failed` or `quarantined`; common causes: corrupt PDFs, empty text, hash mismatch (storage corruption or tampering — treat as security).
