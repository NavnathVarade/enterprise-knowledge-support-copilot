# Terraform / OpenTofu (Phase 38): AWS infrastructure

`infrastructure/terraform/` provisions the cloud resources the Kubernetes/Helm deployment needs.
AWS is the chosen target (the manifests already assume S3 + KMS, RDS-style Postgres, Redis, Kafka).

## Layout

    modules/network   VPC, 2-3 AZ public/private subnets, NAT, S3 gateway endpoint, flow logs
    modules/storage   KMS key (rotation on), private versioned SSE-KMS documents bucket
    modules/data      RDS PostgreSQL 16, ElastiCache Redis, MSK Kafka, Secrets Manager entries
    modules/eks       EKS cluster, managed node group, IRSA role for the app
    envs/staging      cheaper, not zone-resilient (1 NAT, single-AZ DB, no Redis replica)
    envs/production   3 AZ, NAT per AZ, Multi-AZ DB, deletion protection, Redis replica

## Use

    cd infrastructure/terraform/envs/production
    cp backend.hcl.example backend.hcl && cp terraform.tfvars.example terraform.tfvars   # edit
    tofu init -backend-config=backend.hcl
    tofu plan -out plan.bin && tofu apply plan.bin

`backend.hcl` and `*.tfvars` are git-ignored; the committed examples hold placeholders only.
Create the state bucket (private, versioned, KMS-encrypted) and lock table first, outside this code.

## Security decisions

- **Private by default:** RDS, Redis and MSK are in private subnets; their security groups admit
  ingress only from the EKS node security group (a test fails on any CIDR rule).
- **Encryption:** one customer-managed KMS key per environment for RDS, Redis, MSK, S3, EBS,
  CloudWatch logs, Secrets Manager and Kubernetes Secrets. TLS everywhere (`rds.force_ssl`, Redis
  in-transit, MSK `TLS` + SASL/SCRAM only, S3 deny-insecure-transport).
- **No DB password in state:** RDS generates and stores it in Secrets Manager
  (`manage_master_user_password`).
- **Known weakness:** the Redis AUTH token and the Kafka SCRAM password are generated by Terraform
  and therefore **are in state**. The state backend must be encrypted and tightly access-controlled;
  rotate by tainting the `random_password` resources. Moving them to rotation-managed secrets is
  future work.
- **Kubernetes API** is private unless `public_api_cidrs` is set; `0.0.0.0/0` is rejected.
- **Nodes:** IMDSv2 only with hop limit 1 (pods cannot read node credentials), encrypted disks.
- **IRSA:** the app role trusts exactly `system:serviceaccount:ekc:ekc`; it can read/write the
  documents bucket and read the three secrets, nothing else. The Kubernetes ServiceAccount must be
  annotated with the `app_role_arn` output. The manifests set `automountServiceAccountToken:
  false`; the EKS pod-identity webhook injects its own projected token, but this interaction has
  **not been tested**.

## Wiring to the application (manual steps, not automated here)

1. Install pgvector: `CREATE EXTENSION vector;` as the master user, then run the `db-roles` SQL for
   the migration/app/analytics roles (`infrastructure/sql/`). Terraform does not connect to the DB.
2. Create the Kafka topics with the topics-init job. **The MSK SASL/SCRAM listener is port 9096**;
   the Kubernetes ConfigMap, Helm values and NetworkPolicy default to 9093: override
   `KAFKA_BOOTSTRAP_SERVERS` with the `kafka_bootstrap_brokers` output and allow 9096 egress.
3. Feed the Secrets Manager ARNs (output `secret_arns`) into the External Secrets operator
   (`infrastructure/kubernetes/examples/externalsecret.yaml`).
4. Use `rds_endpoint` / `redis_primary_endpoint` for `DATABASE_URL` / `REDIS_URL` (`rediss://`; `DATABASE_URL` must end with `?ssl=require` or stronger, otherwise the app refuses to start).
